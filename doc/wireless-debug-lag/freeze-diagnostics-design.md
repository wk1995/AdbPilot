# 手机卡死诊断优化方案

2026-11-11 · 待实施 · [现场记录](incident-2026-11-11.md) · [首版技术方案](technical-design.md)

## 当前分支的能力缺口

首版 `adbpilot lag record` 一次测一条 ADB 传输。它可以记录超时，但当手机本机无响应、USB 和 Wi-Fi 同时失效时，依赖设备端命令的帧、CPU 和温控数据也会中断。采集窗口跑完时，即使探针全部超时，报告仍会显示“已完成”。[采样与报告实现](../../adbpilot/lag.py#L223)

这次需要人工同时检查三条手机传输、电脑上的 ADB server 和模拟器，重启后再补查系统记录。AdbPilot 当前缺少一个能在卡死前启动、在手机失联后继续保存证据、恢复后补采的流程。整机卡死时，能否保留手机内部证据还取决于卡死前是否已采集，以及系统能否将数据写入存储。

## 先修正诊断结果和采集负载

1. **明确区分连接在线和命令可用。** 保留现有 `status` 表示会话执行结果，新增独立的诊断状态，避免旧报告和脚本受影响。主机列表响应且目标仍显示 `device`、同时设备命令连续两次超时时，立即记录并显示“ADB 显示在线，设备命令无响应”。主机列表查询超时单独记录。只有用户报告手机本机也无法操作，才在报告中加入“手机本机无响应（用户确认）”。[ADB 主机服务定义](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/dev/services.md)
2. **连续超时后降低探测频率。** 默认每 3 秒测一次，单次最多 2 秒。连续两次超时后立即保存当前证据，随后每 15 秒最多一次轻量探测。跳过帧、CPU、温控等设备端查询，并在报告标明跳过原因。主机侧列表仍可用于观察离线或重新上线。CLI 报告分别显示成功、命令超时、主机查询失败和因降频跳过的样本数。全程没有成功样本时，耗时统计为空。
3. **降低 GUI 设备监听的查询负载。** GUI 每 3 秒尝试刷新。在至少两条在线传输时，当前去重会逐个通过设备端读取 `ro.serialno`，单次最多等 5 秒，设备列表与恢复逻辑共用服务锁。建议先读主机列表并更新 UI，后台只对新出现或变化的传输做有界的身份读取。对已验证身份按当前 ADB server 会话和 transport ID 缓存，失败则退避。传输消失、重连、ADB 路径变更或检测到 server 更换时清理相关缓存。身份未验证时保留独立的传输行，锁定设备继续使用原有目标。这条路径会增加设备端调用，是否与卡死有关仍需对照。[GUI 设备监听](../../adbpilot/gui.py#L1799) · [去重查询](../../adbpilot/client.py#L154)

## 增加一次卡死现场诊断会话

| 阶段 | 拟采集的证据与行为 |
| --- | --- |
| 复现前 | 用户显式启动诊断并选定同一手机的 USB、Wi-Fi 传输。手机响应正常时核对归属，使用会话内标签保留映射。Wi-Fi 重复条目保留在列表快照里，正常采样时选一条主无线传输。记录用户标注的无线调试、小米互联服务、妙想桌面和 AdbPilot GUI 状态。 |
| 复现中 | 按有界时长轮流测 USB 与主 Wi-Fi，同一手机最多一个设备端探针在途。主机快照、各传输探针和 Enter 打点共用主机单调时间轴。记录实际开始时间，用于判断两个传输的故障窗口是否重合。首轮可用 5 分钟上限和最近 2 分钟的主机侧记录作为待验证默认值。 |
| 出现异常 | 保存卡死前时间线、第一次失败、最后一次成功、主机侧连接列表及用户打点。固定住这份故障快照，再追加低频恢复事件。报告增量写到 Mac，避免只能等会话退出才导出。每次落盘保留上一份完整快照。缺少可用手机证据时标明原因。 |
| 恢复后 | 用户确认目标手机后，通过 USB 补采启动时长、启动原因和故障时间附近可访问的系统异常条目。把新启动周期写成独立区间。`reboot` 单独出现时只说明系统记录了一次重启。若有需要，由用户单独触发完整 bugreport。 [Android 启动原因定义](https://source.android.com/docs/core/architecture/bootloader/boot-reason) · [Android bugreport](https://developer.android.com/studio/debug/bug-report) |

发现传输 ID 变化或身份无法确认时，结束该传输的设备端采样，主机侧时间线继续保存。恢复后的传输由用户确认关联。探测过程不自动重启手机或 ADB，也不自动开关无线调试或小米互联服务。报告使用会话内标签，默认省略序列号、地址、原始日志和凭据。

手机内部根因仍需额外证据。可选的下一阶段是在手机还可操作时启动限时 Perfetto，试验按周期写入手机文件并设置大小上限。断开 ADB 后设备仍有机会继续录制，整机卡死或强制重启时，最后几秒或整份 trace 都可能缺失。先在目标机验证开销、文件权限和重启后可读性，再把它加入一键流程。 [Perfetto 后台采集](https://perfetto.dev/docs/learning-more/tracing-in-background) · [Perfetto 文件写入与大小上限](https://perfetto.dev/docs/concepts/config)

## 如何验收

先用模拟 ADB 复现“列表仍在线，所有手机命令超时”。验证提示、即时落盘、退避、跳过重采集、旧报告读取以及断线或 transport ID 重用时的行为。GUI 验证多条在线传输稳定后，每次刷新只查主机列表，身份读取不会挡住设备列表更新，锁定目标不会随去重变化切到其他设备。

真机对照用同一台手机，USB 始终连接，保持同一个手机页面、动作和网络。每组记录三个独立观察值：手机触摸响应、Mac 上妙想桌面画面、ADB 命令响应。把妙想桌面已连接但空闲和正在控制分别记下。

| 场景 | 无线调试 | 小米互联服务和妙想桌面 |
| --- | --- | --- |
| USB 基线 | 关闭 | 服务关闭 |
| 只加无线调试 | 开启，ADB 已连 | 服务关闭 |
| 只加跨端控制 | 关闭 | 服务开启，妙想桌面控制手机 |
| 叠加现场条件 | 开启，ADB 已连 | 服务开启，妙想桌面控制手机 |

前两组使用手机本机完成同一动作。后两组先在服务开启、妙想桌面空闲时重复本机动作，再用 Mac 控制完成同一动作。出现明显无响应时结束该轮并保存主机侧证据。恢复后的正常 USB 读数用于标记恢复时点，重启和功能开关的影响需要分开验证。
